# 0016: セッション単位のカウンタは max_over_time で集計する

- 状態: 採用
- 日付: 2026-08-30

## 状況

Claude Code の OTel メトリクスは `session_id` をラベルに持つ。
セッションごとに別の系列が生まれ、セッションが終わると値が止まる。
系列は最初のエクスポート時点で既に累積値を持って現れ、そこから先しか増えない。

`increase()` や `rate()` は窓の中で観測できた増分しか返さないので、この形のカウンタでは取りこぼす。

- 処理が最初のスクレイプより前に終わった短いセッションは、系列が平坦になり増分が 0 になる
- 長いセッションでも、最初のエクスポートまでに積まれた分は増分として現れない

9 セッション流したときの実測値。

| パネル | `increase()` | 実際 |
| --- | --- | --- |
| 本日のコスト | $0.058 | $0.422 |
| セッション数 | 0 | 9 |
| 実稼働時間 | 0 秒 | 180.7 秒 |

「No data」ではなく `0` が出るため、正しい値に見えてしまう。

## 判断

集計値のパネルは `max_over_time()` を使う。系列ごとの最終値を取り、それを足す。

トークンの時系列は Prometheus では復元できない。最初のエクスポート分は増分として存在しないため。
Loki の `api_request` イベントが 1 リクエストごとの `input_tokens` / `output_tokens` /
`cache_read_tokens` / `cache_creation_tokens` を持っているので、そちらから集計する。
Codex 系のパネルが既に同じ形（[0010](0010-codex-from-logs.md)）。

落とした案。

| 案 | 落とした理由 |
| --- | --- |
| `session_id` をラベルから外す | セッションごとに累積値が別々に始まるため、1 系列に潰すとカウンタリセットとして扱われる |
| delta temporality にして `deltatocumulative` を挟む | ハーネス側の設定に手を入れる必要があり、このリポジトリの範囲を超える |

## 結果

- 集計値が実測と一致する。突き合わせは Loki のイベント合計でできる
- `query_source 別トークン` の凡例が生の値（`sdk`、`agent:builtin:Explore` など）に変わる。
  Prometheus 側の `main` / `auxiliary` / `subagent` より細かい
- `max_over_time` は窓をまたぐ系列を両方の窓に数える。日次パネルでは日付をまたいだセッションが両日に載る
- Claude Code が `session_id` を持たない形でメトリクスを出すようになったら、この判断は見直す
